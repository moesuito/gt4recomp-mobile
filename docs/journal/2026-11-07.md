## Round 12: the virtual pad's wide buttons take their width from the view width (2026-11-07)

Checklist A34 (read-only check): `docs/CONTROLS.md` says an element's `width` is a fraction of the screen **width** and
the editor (`ui/js/virtual-pad-model.js`) draws it that way, but `native/virtual_pad.cpp` treated it as a height fraction
and `VirtualPadView.kt` multiplied by the view height. On a 19.3:9 phone the wide buttons (L1/R1/L2/R2, Select/Start)
were therefore narrower than the editor preview; the square elements were right.

**Fix.** The parser records whether the layout gave a width (`LayoutElement.wide`) and `Pad::geometry` carries it as a
ninth float per element; `VirtualPadView` uses `width x the view width` for a wide element and keeps the height base for
a square one. The new `pixel_width()` in the native library states the contract (and is what the fixture tests); the
editor model was already correct. Heights, sticks, the D-pad and the face buttons are untouched.

**Defaults.** The shipped layout's 0.16 (L1/R1/L2/R2) and 0.11 (Select/Start) are the documented width fractions: with
them the pairs sit side by side (a 0.01 fraction gap) at both shapes, and the layout was not tuned to the old height
base. No default value changed; the next APK shows them at the editor's width, slightly wider than today's game on the
phone. `docs/CONTROLS.md` now states the game rule too.

**Tests.** `virtual_pad_fixture` (compiled alone with clang-cl, since the full native build needs the pinned private
library) passes all groups; the new `check_width_contract` asserts at 2400x1080 and 3088x1440 that a wide element's
pixel width is width x the view width, a square element's is height x view height, the default L1 and lstick rectangles
(0.22..0.38 x 0.04..0.16 for L1; 0.058..0.202 and 0.055389..0.204611 for lstick), and that the default's wide pairs sit
side by side. The focus checks add the same default rectangles on the editor model: 463/463 en-US and 470/470 pt-BR at
1366x768, 2400x1080 and 1080x2400, nav-test 293/293. No Rust change, so no cargo test; no APK.
